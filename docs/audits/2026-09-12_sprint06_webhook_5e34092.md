## Prueba funcional (detalle)

1. Se insertó una fila de prueba en `public.notifications` (con `water_event_id` real y `app_user` real) — equivalente a lo que genera el trigger `notify_water_event`.
2. El edge-runtime registró: `serving the request with supabase/functions/notify-push` → el webhook disparó la función.
3. No se envió push real (sin `FCM_SERVICE_ACCOUNT_JSON` configurado; la función responde push omitido por diseño).
4. Fila de prueba eliminada (`DELETE FROM notifications WHERE title='AUDIT_PROBE'`); verificado `count=0`. Estado de la relación sin drift (1 fila restante de datos previos).

## Discrepancias / notas

- **Ninguna discrepancia funcional.** El estado actual corrige los 3 críticos del baseline (`404a4bd`): migración 00018/00019 aplicadas, `notify-push` desplegada, webhook registrado y `pg_net` instalada.
- **Nota de diseño (no bloquea):** el webhook en self-hosted usa `supabase_functions.hooks` (no el Dashboard de Cloud). `config.toml` comenta "trigger vía supabase_functions.http_request" — el mecanismo real es la fila en `hooks` gestionada por el CLI/`supabase functions deploy`. Funciona; solo aclarar en docs si se documenta el self-hosted.
- **Pendiente operativo (producción, no auditoría):** para que el push llegue al dispositivo falta inyectar `FCM_SERVICE_ACCOUNT_JSON` vía `supabase secrets set` en el entorno destino. Fuera del alcance de esta validación (no se tocó).
